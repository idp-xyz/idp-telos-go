02平台全景

五个子系统彼此独立：各有自己的仓库、存储、身份边界和发布节奏，只经公开接口与登记的契约协作。平台仓库只编排发布件和做集成验收，不含任何组件源码。

状态权威只有一个：Workspace 持有工作空间、安装与收件箱视图；HOST 持有 AgentRun；EER 持有 Execution、审批与证据；CMI 持有上下文包与记忆；MCP 持有工具注册与调用审计。收件箱事项只是视图——审批由 EER 决定，事项由生产者结束（catalog/ownership.yaml，由 tools/platform.py check 校验恰好一个权威）。

04跨系统路径

三条路径都在同一套平台上运行：一个 PostgreSQL（每组件一库）、Keycloak 26.8.1（https 发行者）、四个组件从各自仓库构建的镜像，以及 Temporal。验收脚本在每条路径结束时，到所有相关系统里核对记录是否一致。

PATH A　问答与辅助决策：Workspace → HOST → CMI

PATH B　高可靠执行：EER T2 审批经 Workspace 决定

PATH C　EER Intelligence 从平台 CMI 取 Decision 上下文

EER 的 API 没有启动 Decision 的入口，平台里没有触发它的产品路径。因此 PATH C 在平台上运行 EER 自己的 Decision × CMI 测试：Keycloak 服务账号 eer-intelligence 向平台的 CMI 解析上下文、做 Decision、写回 episodic 记忆；第二次 Decision 在上下文中看到第一次的记忆。测试在干净环境中运行，因为 EER 的 Intelligence 平面拒绝在 Runtime 凭据旁启动（ADR-032）。

06身份与令牌

用户令牌从不交给应用，也不跨越不该跨越的边界：每个下游只收到发给自己受众的令牌，每个服务以自己的工作负载身份调用别人。

08验证中发现并修复的缺陷

这些缺陷都只在更高一层的验证中才暴露——这是逐层上移验证的价值所在。每一项都已修复，并留下能再次抓住它的测试或检查。

#位置缺陷由谁发现
1Workspace 壳沙箱 frame 缺 allow-same-origin 时来源为 "null"，桥的来源校验会丢弃全部消息；改为保留应用自身来源，并拒绝装入与壳同源的应用Chromium 冒烟
2Workspace 壳每次渲染新建 API 客户端，导致请求风暴（浏览器报资源不足）Chromium 冒烟
3Workspace 壳换用正确令牌后仍显示上一个令牌的错误用户实际使用
4Workspace 服务目标凭据校验允许 webhook 目标同时带 agent 字段，与契约不一致契约拒绝用例
5平台目录 / READMEREADME 记录 EER 依赖 host 1.2.0，实际钉住 1.5.0；HOST 被误列为 mcp 契约的消费方兼容性矩阵
6HOST · Workspace两处消费契约却没有消费方测试兼容性矩阵
7idp-host 清单网络策略没有到 idp-cmi 的出站，上下文包会被阻断k8s 检查
8HOST · Workspace 命名空间缺少被调方用来接纳客户端的命名空间标签（MCP 网关、idp-host），工具调用与 host.run 会被阻断k8s 检查
9MCP · HOST · CMI 清单commonLabels 把组件自己的名称标签写进指向 PostgreSQL、kube-dns、MCP 网关的选择器，规则从此匹配不到任何 Podkind（网络策略生效）
10CMI 评估集文档按数据库时钟定日期而评估用固定时钟，nDCG 随运行时刻在 0.84 与 0.8356 间漂移，CI 失败CI 检索评估
11EER 测试CMI 联调测试假定请求者恒为 eer-intelligence，只在开发凭据下成立平台 PATH C
12D29 集成测试测试以无权限的主体断言机密内容可被检索；改为直接校验全文索引集成测试
13平台配置HOST 只在开发模式允许明文连模型；EER 只接受 https 发行者且只用 https 取 JWKS——平台改为按各组件的安全规则配置，而不是放宽它们平台验收
第 7–9 项在 compose 环境中完全看不出来：compose 不执行 NetworkPolicy。它们若进入生产，会表现为 HOST 取不到上下文、调不了工具，甚至 CMI 连不上数据库。

09部署形态

整平台 compose

deploy/compose/platform.yaml：一个 PostgreSQL（每组件一库，EER 的角色由其自带 SQL 建立）、Keycloak（https 7443 给浏览器与发行者，http 7080 供容器取令牌与公钥）、CMI、HOST（含模型替身或经转发器连本机模型）、Workspace、EER 全套与 Temporal。所有服务只读根文件系统、去除全部能力。

EER 镜像由其 tools/development/runtime_image_offline.sh 离线构建；本机已有的 idp-pulsar 占用 18080，EER 使用 18180–18182。

Kubernetes（暂缓）

五个组件都有自带清单与一致性测试；平台的 deploy/kubernetes/kind 按组件仓库原样组合三个公开组件，只在叠加层中改为开发令牌、明文 HTTP、本地镜像，并加集群内 PostgreSQL、模型替身与建登录 / 租户的 Job。按决策，Kubernetes 的后续工作暂缓；已有清单、检查与 kind 工作流保持现状。

10遗留事项

事项现状需要
带 EER 的整平台验收进 CIidp-eer 是私有仓库，平台 CI 检出不了；其相关检查标为 NOT_RUN（允许），从不记为通过需你提供只读访问凭据
镜像发布、签名与 SBOM镜像只在本机构建，发布清单记录本机镜像 id需你决定发布位置与可见性
EER 真实连接器Actor 由 EER 自带的确定性替身执行外部条件真实业务系统
CMI 向量检索用真实模型本机模型服务没有 /v1/embeddings外部条件嵌入端点
真实审批系统与 OPA 策略包CMI 的审批核验与 PDP 只对替身验证过外部条件
Kubernetes 后续按决策暂缓以后再说
